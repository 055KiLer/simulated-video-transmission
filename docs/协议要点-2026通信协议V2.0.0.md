## 1. 串口物理层（§1.1）

- 通信性质：**8 位数据位，1 位停止位，无硬件流控，无校验位**（8N1）

**表 1-1 波特率 ↔ 物理接口**

| 物理接口 | 波特率 |
|---|---|
| 电源管理模块 ←→ 机器人 | 115200 |
| **自定义控制器 ←→ 选手端** | **115200** |
| **图传发送端 ←→ 机器人** | **921600** |

> 🔑 这张表就是孙说的"数据格式不一样"的关键之一：**两端波特率差 8 倍**（115200 vs 921600）。

## 2. 帧格式（表 1-2 / 1-3 / 1-4）

```
| frame_header (5B) | cmd_id (2B) | data (n B) | CRC16 (2B) |
|  SOF | data_length | seq | CRC8 |              |            | 整包校验 |
   1B      2B         1B    1B
```

| 域 | 偏移 | 大小 | 说明 |
|---|---|---|---|
| SOF | 0 | 1 | 数据帧起始字节，**固定 0xA5** |
| data_length | 1 | 2 | data 段的长度 |
| seq | 3 | 1 | 包序号 |
| CRC8 | 4 | 1 | **帧头**的 CRC8 校验 |
| cmd_id | 5 | 2 | 命令码 |
| data | 7 | n | 数据段 |
| CRC16 | 末尾 | 2 | **整包**校验 |

**校验参数（附录一）**
- CRC8：生成多项式 `G(x)=x⁸+x+x⁴+1`，初值 `0xFF`，查表法
- CRC16：初值 `0xFFFF`，查表首项 `0x0000, 0x1189, 0x2312…`（即反射多项式 `0xA001`），`Append_CRC16_Check_Sum` 中**低字节在前、高字节在后**
- 附录一给了完整 C 代码，直接抄进工程即可，不要自己写

> ✅ 三条链路（常规 / 图传 / 雷达无线）**共用同一套帧格式**（§1.1 统领整章）。所以"转格式"主要是转**波特率 + 电平**，不是重写帧结构。

## 3. 三条数据链路（§1.1 末尾）

| 链路 | 转发方 | 物理入口 |
|---|---|---|
| 常规链路 | 裁判系统服务器 ↔ 主控模块 | **电源管理模块的 User 串口** |
| **图传链路** | 裁判系统选手端 ↔ 图传模块 | **图传模块（发送端）的串口** |
| 雷达无线链路 | 裁判系统信号发射源 → 雷达 | 电磁波 |

图传链路拓扑（文档示意图原文顺序）：

```
机器人 ← 图传发送端 ← 图传接收端 ← 选手端 ← 自定义控制器 / 自定义客户端
```

**我们要替代的就是"图传发送端 ← 图传接收端 ← 选手端"这段无线链路，用一根有线串口直接喂给机器人。**
板子的输出端等价于"图传发送端"，所以对接机器人侧必须按 **921600** 来。

**链路质量指标（文档给的官方口径，做验收参考）**
- 正常工作状态：数据延迟约 **130ms**，丢包率 **< 1%**
- 赛场网络恶劣：延迟约 **200ms**，丢包率约 **3%**

## 4. 图传链路相关命令码（§1.4 + 表 1-5）

| 命令码 | 数据段 | 说明 | 发送方 / 接收方 | 频率上限 |
|---|---|---|---|---|
| **0x0302** | 30 B | 自定义控制器与机器人交互数据 | 自定义控制器 → 选手端图传连接的机器人 | 30Hz |
| **0x0309** | 30 B | 机器人 → 自定义控制器 的数据 | 己方机器人 → 对应操作手选手端连接的自定义控制器 | 10Hz |
| 0x0310 | 300 B | 机器人发送给自定义客户端 | 己方机器人 → 图传链路 → 选手端连接的自定义客户端 | 50Hz |
| 0x0311 | 30 B | 自定义客户端发送给机器人的自定义指令 | 对应操作手选手端连接的自定义客户端 → 图传链路 → 己方机器人 | 75Hz |
| 0x0306 | 8 B | 自定义控制器与选手端交互数据（模拟键鼠，§1.5 **非链路数据**） | 自定义控制器 → 选手端 | 30Hz |
| 0x0307 | 103 B | 选手端小地图接收路径数据 | 哨兵/半自动控制机器人 → 对应操作手选手端 | 1Hz |

数据结构（表 1-39 / 1-40）都是裸自定义数据：

```c
typedef _packed struct {
    uint8_t data[x];      // 0x0302 / 0x0309: 30 字节
} custom_robot_data_t;
```

> 🔑 **0x0302（控制器→机器人）和 0x0309（机器人→控制器）是双向的** → 桥接板必须做**全双工双向透传**，不能只接一个方向。这条把上一版计划里的"待确认问题 1"直接回答了。
>
> 另外注意 0x0302 频率上限 30Hz × 30 字节 ≈ 900 B/s ≈ 7.3 kbps，相对 921600 带宽极小，**MCU 完全无压力，F1 足够**（孙说的"F1 应该够"成立）。

## 5. ⚠️ 一个必须提前问的风险点

文档 §2.2.12 `RobotModuleStatus`（机器人模块状态）里，**"图传模块状态"是官方检测项之一**：

| 数据编号 | 类型 | 用途 |
|---|---|---|
| 8 | uint32 | **图传模块状态（0=离线，1=在线，2=因安装不规范被视为离线）** |

也就是说裁判系统会检查图传模块在不在线、装得规不规范。用有线桥接替代图传，**有可能被判为"图传模块离线"或"安装不规范"**。

这不是技术问题，是规则/检查问题 —— 必须找孙晨航确认队里怎么处理的（是真图传模块仍在位、只是额外加一条有线链路，还是官方允许这种替代）。

## 6. 其他可能用得上的

- **附录二 机器人 ID 编号**：红方 1~11（1 英雄、2 工程、3/4/5 步兵、6 空中、7 哨兵、8 飞镖、9 雷达、10 基地、11 前哨站），蓝方 101~111 同序。部分命令需校验发送者/接收者 ID。
- **自定义客户端可通过 UDP 监听 3334 端口获取图传码流数据**，帧率 60 帧（§2 附近）。如果以后要做视频侧，入口在这里。
- 文档修改日志：V2.0.0 明确了"波特率和物理接口的对应关系"（就是表 1-1）、修订了 0x0309 / 0x0310 等命令、删除了 0x0304。**说明表 1-1 是新加的，早期资料/网上教程的波特率可能过时，别照抄旧例程。**

## 7. 这份文档里没有的（仍需外部资料）

以下本项目必需、但本通信协议**完全没写**，必须靠硬件手册或问队里：

1. **RS232 / DB9 物理接口** —— 全文没有出现 "RS232"、"DB9" 字样。自定义控制器那个 DB9 口的引脚定义、电平标准、是 DTE 还是 DCE 接法，得看**自定义控制器的硬件手册**。
2. **GH1.25 连接器的线序** —— 文档只说"图传发送端←→机器人"，没给机器人侧那个座子的引脚定义。
3. **供电** —— 谁给板子 5V/3V3。
4. **板子尺寸/安装位置约束**。

## 8. 谁走哪条路：选手端 / 自定义控制器 / 自定义客户端

这三个东西容易混，但走的路完全不同，直接决定"你的板子搬什么"：

| 数据 | 命令码 | 路径 | 经过图传链路？ |
|---|---|---|---|
| **开车/打弹的操控**（键鼠控制指令） | 官方选手端产生，走**常规链路** | 选手端 → 服务器 → 主控模块 → 电源管理模块 User 串口（115200）→ 机器人 | ❌ 不经过 |
| 自定义控制器**模拟键鼠**给选手端 | **0x0306**（8B，§1.5 非链路数据） | 自定义控制器 → 选手端（115200） | ❌ 不经过 |
| 自定义客户端（PC）的键鼠指令 | protobuf `KeyboardMouseControl`（§2.2.1，UDP） | 文档原文："该数据将通过**相机图传模块（接收端）**发送给机器人" | ✅ 经过，但是网络侧 |
| **自定义控制器的自定义数据 → 机器人** | **0x0302**（30B，≤30Hz） | 自定义控制器 → 选手端 → 图传接收端 → 图传发送端 → 机器人 | ✅ **就是这条** |
| **机器人 → 自定义控制器** | **0x0309**（30B，≤10Hz） | 反向 | ✅ **就是这条** |
| 自定义客户端 ↔ 机器人 | 0x0310（300B，≤50Hz）/ 0x0311（30B，≤75Hz） | 图传链路 | ✅ 经过，但那是 PC 不是控制器 |
| 机器人多机交互 | 0x0301（118B，≤30Hz） | 常规链路 | ❌ |

> 结论：**本板搬运的是 0x0302 / 0x0309 这一对"自定义数据"**，不是裁判系统的全量广播，也不是官方的遥控指令。
> 协议 §1.1 明确：裁判系统**没有任何"遥控指令"命令码**（没有底盘速度、云台角度、发弹指令这些字段），
> 操控是通过"键鼠"语义由选手端/自定义客户端转换成机器人数据的。所以"把操控发给系统"这件事在协议层不存在，
> 除非队里自己把控制语义塞进 0x0302 的 30 字节里，那它才会路过你的板子——但对裁判系统来说那 30 字节仍然是不透明自定义数据。

### 对上一版计划的修正

| 上一版的说法 | 实际情况 |
|---|---|
| "帧结构可能是 A5 5A + length + seq + payload + CRC8，待核实" | ❌ 不对。真实是 **SOF 单字节 0xA5**（没有 0x5A），帧头 5 字节内含 CRC8，**整包再套一个 CRC16** |
| "需要重写帧头/命令 ID/校验" | ❌ 大概率不需要。三条链路共用同一帧格式，转的是**波特率 + 电平** |
| "单向还是双向待确认" | ✅ 已由协议确定：**双向全双工**（0x0302 出、0x0309 回） |
| "两端波特率待确认" | ✅ 已由协议确定：**进 115200 / 出 921600** |
| "F1 够用" | ✅ 成立，带宽需求 <10kbps |
